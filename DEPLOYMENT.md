# Спецификация сборки и деплоя Buchhaltzar

Версия документа: 0.1.0  
Цель: воспроизводимая сборка и безопасный выпуск мобильного совместимого Obsidian-плагина.

## 1. Артефакт поставки

Минимальный устанавливаемый пакет:

```text
buchhaltzar/
├── manifest.json
├── main.js
└── styles.css
```

Дополнительно допускается `versions.json`, если используется механизм совместимости версий Obsidian.

Исходный TypeScript, карты исходников, тестовые данные, локальные конфиги, секреты и `.env` не входят в пользовательский релиз.

## 2. Manifest

Начальный вариант:

```json
{
  "id": "buchhaltzar",
  "name": "Buchhaltzar",
  "version": "0.1.0",
  "minAppVersion": "1.7.0",
  "description": "Local-first personal and project accounting in an Obsidian vault.",
  "author": "Buchhaltzar Project",
  "isDesktopOnly": false
}
```

`minAppVersion` перед первым релизом определяется фактически использованными API и проверяется на устройствах. Нельзя повышать или понижать его без проверки совместимости.

## 3. Инструменты

Рекомендуемый стек:

- TypeScript;
- Obsidian API;
- React;
- esbuild;
- Vitest;
- ESLint;
- Prettier;
- YAML-парсер без Node-only зависимостей;
- библиотека десятичной арифметики либо собственный тип `Money` на целых minor units;
- pnpm с lock-файлом.

Каждая runtime-зависимость проверяется на отсутствие обязательных Node/Electron API.

## 4. Команды проекта

Ожидаемые команды:

```json
{
  "scripts": {
    "dev": "node esbuild.config.mjs --watch",
    "build": "node esbuild.config.mjs --production",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "format:check": "prettier --check .",
    "test": "vitest run",
    "test:coverage": "vitest run --coverage",
    "verify": "pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm build",
    "package": "node scripts/package-release.mjs"
  }
}
```

Команда `verify` является обязательным локальным и CI-шлюзом перед выпуском.

## 5. Окружения

### 5.1. Development vault

Разработка ведётся только в отдельном тестовом vault. Нельзя тестировать операции записи на основном пользовательском vault.

```text
test-vault/
└── .obsidian/
    └── plugins/
        └── buchhaltzar/
```

### 5.2. QA vault

Содержит:

- пустой vault;
- 100 тестовых операций;
- 10 000 синтетических операций;
- повреждённый YAML;
- неизвестную версию схемы;
- дубликаты ID и idempotency key;
- несколько валют;
- чеки разных размеров.

### 5.3. Production vault

Установка выполняется только после резервного копирования. Первая версия создаёт новое чистое учётное пространство и не читает старые Google-таблицы или другие системы учёта.

## 6. Конфигурация сборки

Сборка должна:

1. Создавать единый `main.js`.
2. Исключать пакет `obsidian` из bundle.
3. Не включать Node polyfills.
4. Минифицировать production-артефакт.
5. Не публиковать source map в пользовательском релизе, если он раскрывает пути или исходники.
6. Завершаться ошибкой при наличии запрещённых импортов.

Запрещённые runtime-импорты для mobile-сборки:

```text
fs
node:fs
path
node:path
electron
child_process
net
tls
```

Если desktop-only функция когда-либо потребуется, она должна быть изолирована, динамически загружаться только после проверки `Platform.isDesktopApp` и не влиять на mobile bundle. Для MVP такие функции не планируются.

### 6.1. Контроль полной автономности

Production bundle не должен содержать или вызывать:

- `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`;
- HTTP-клиенты и облачные SDK;
- удалённые шрифты, изображения, стили или скрипты;
- аналитику, crash reporting и телеметрию;
- проверку лицензии или авторизацию через сеть;
- автоматическую загрузку моделей и справочников.

Все необходимые шрифты, иконки, словари, шаблоны и схемы поставляются внутри релиза либо создаются локально. CI проверяет исходники, lock-файл и собранный `main.js` на сетевые вызовы и URL. Исключения для runtime не допускаются.

Тест автономности запускает собранный плагин при заблокированной сети и проверяет полный сценарий: инициализация → приход → расход → перевод → сторно → поиск → перестройка индекса → повторный запуск.

## 7. Контроль секретов

CI обязан проверять:

- токены Telegram;
- API-ключи Google/Gemini;
- bearer-токены;
- приватные ключи;
- содержимое `.env`;
- случайно добавленные финансовые данные.

Рекомендуется secret scanner и отдельный тест, запрещающий известные шаблоны токенов.

Любой секрет, однажды попавший в Git или опубликованный скрипт, считается скомпрометированным и должен быть заменён.

## 8. CI

На каждый pull request выполняются:

1. Установка зависимостей строго по lock-файлу.
2. Проверка форматирования.
3. ESLint.
4. TypeScript typecheck.
5. Unit-тесты.
6. Integration-тесты файлового адаптера на mock vault.
7. Production build.
8. Анализ bundle на запрещённые импорты.
9. Secret scan.
10. Анализ bundle на сетевые вызовы и удалённые runtime-ресурсы.
11. Автономный integration-тест с заблокированной сетью.
12. Проверка соответствия версии в `manifest.json`, package metadata и Git tag для релиза.

Сборка релиза выполняется CI из чистого checkout, а не загружается с компьютера разработчика.

## 9. Версионирование

Используется Semantic Versioning:

- `PATCH` — исправление без изменения схемы или пользовательского поведения;
- `MINOR` — совместимая функция или новая необязательная версия схемы;
- `MAJOR` — несовместимое изменение формата или API.

Версия схемы транзакции живёт отдельно от версии плагина:

```text
plugin: 0.4.2
schema: buchhaltzar.transaction.v1
```

Обновление плагина не должно автоматически означать миграцию всех файлов.

## 10. Миграции

Каждая миграция:

1. Имеет уникальный ID и версии `from/to`.
2. Сначала выполняет dry-run.
3. Показывает число затрагиваемых файлов.
4. Создаёт резервную копию или требует подтверждённую резервную копию.
5. Не изменяет неизвестные поля без необходимости.
6. Записывает отчёт.
7. Может безопасно продолжиться после прерывания.
8. Не запускается молча при открытии vault.

Для MVP миграций существующих Buchhaltzar-схем нет. Миграция из Google Sheets и других прежних систем не предусмотрена: проект начинает работу с новыми данными.

## 11. Локальная установка разработчика

1. Создать отдельный тестовый vault.
2. Установить зависимости.
3. Собрать плагин.
4. Скопировать или связать только артефакты в `.obsidian/plugins/buchhaltzar`.
5. Включить Community plugins в тестовом vault.
6. Включить Buchhaltzar.
7. Открыть диагностический экран и инициализировать тестовое пространство.

Разработка плагина всегда проводится на отдельном vault, поскольку ошибка может повредить содержимое хранилища.

## 12. Установка частного релиза

До публикации в Community plugins используется ZIP:

```text
buchhaltzar-0.8.2.zip
├── buchhaltzar/
│   ├── manifest.json
│   ├── main.js
│   └── styles.css
├── install.sh
├── install.ps1
├── install.py
└── Установка.txt
```

Порядок на компьютере:

1. Создать резервную копию vault.
2. Распаковать ZIP и запустить `install.sh` или `install.ps1`.
3. Выбрать хранилище. Установщик сам создаёт `.obsidian/plugins/buchhaltzar/` и отмечает плагин во `community-plugins.json`.
4. Открыть vault в Obsidian и при необходимости разрешить сторонние плагины.

На телефоне из архива копируют папку `buchhaltzar` в `.obsidian/plugins/` (нужно показать скрытые файлы).

## 13. Публичный релиз

Перед отправкой в каталог сообщества:

- manifest соответствует правилам Obsidian;
- нет телеметрии;
- нет передачи содержимого vault;
- runtime bundle не содержит сетевого клиента и удалённых ресурсов;
- поддерживается mobile;
- есть политика обработки чеков;
- есть инструкция резервного копирования;
- лицензия совместима со всеми зависимостями;
- репозиторий содержит воспроизводимую сборку;
- GitHub Release содержит `main.js`, `manifest.json`, `styles.css`;
- tag совпадает с версией manifest.

Публикация Community plugin требует прохождения актуальной процедуры Obsidian и проверки по официальным правилам на момент выпуска.

## 15. Rollback

Откат плагина и откат данных рассматриваются отдельно.

### 15.1. Откат плагина

Предыдущий релизный ZIP сохраняется. Пользователь может отключить новую версию и установить предыдущую, если формат данных остался совместимым.

### 15.2. Откат данных

Поскольку транзакции создаются отдельными файлами и не переписываются массово, обычный релиз не должен требовать отката данных. Для будущей внутренней миграции схемы используется созданная перед ней резервная копия и отчёт миграции.

Плагин не должен обещать автоматический откат без проверенной резервной копии.

## 16. Наблюдаемость

Диагностический экран показывает:

- версию плагина;
- версию схемы;
- число счетов;
- число валидных транзакций;
- число исключённых файлов;
- состояние индекса;
- время последней перестройки;
- подтверждение отсутствия сетевого модуля;
- безопасный список последних технических ошибок.

Команда «Экспорт диагностики» удаляет комментарии, суммы, контрагентов, изображения, содержимое заметок и пути, способные раскрыть личные данные.

## 17. Резервное копирование

Перед первой production-установкой пользователь должен иметь минимум одну независимую копию vault.

Рекомендуемая политика:

- постоянная синхронизация выбранным пользователем способом;
- периодическая отдельная резервная копия;
- проверка восстановления;
- резервная копия непосредственно перед будущей внутренней миграцией схемы.

История версий синхронизации полезна, но не заменяет независимую резервную копию.

## 19. Условия готовности к разработке

До начала реализации необходимо утвердить:

1. Базовую валюту первоначальной установки.
2. Точный смысл `Кассы`: отдельный счёт или атрибут способа хранения.
3. Правило отрицательного баланса.
4. Возможность редактировать дату операции.
5. Правило округления основного прихода.
6. Состав обязательных полей.
7. Целевые минимальные версии Obsidian, Android и iOS.
8. Модель распространения: частный плагин или Community plugin.
9. Какие локальные правила и словари нужны текстовому помощнику первого релиза.
